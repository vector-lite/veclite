# Light Vector SDK (Veclite) 100万向量内存与性能基准测试报告

## 1. 测试背景与目标

本测试旨在验证轻量级向量 SDK (Veclite) 在 Spring Boot 内嵌场景下的内存开销、单线程写入性能以及本地快照持久化刷盘耗时。
评估目标为 **5 个 Vector Store，每个 Store 存储 20 万条 512 维度的向量（总计 100 万条向量）**，测试 SDK 在标准 Float32 原始浮点存储及连续内存缓冲区（`FloatVectorBuffer`）下的极限指标。

---

## 2. 测试环境与配置

* **操作系统**：macOS (Apple Silicon / ARM64)
* **JDK 版本**：Java 17 (OpenJDK 17.0.8 / JetBrains Runtime JBR-17)
* **JVM 堆内存配置**：`-Xms2g -Xmx6g`
* **测试代码**：`StoreMemoryBenchmarkTest.java`
* **向量数据规格**：
  * **Store 数量**：5 个 (`store_1` ~ `store_5`)
  * **单 Store 向量数**：200,000 条
  * **总向量数**：1,000,000 条 (100 万条)
  * **向量维度**：512 维 (Float32)
  * **距离度量**：余弦相似度 (`COSINE`)
  * **文档载荷 (Payload)**：包含业务 ID (`String`)、文本描述 (`text`) 以及 JSON 元数据 (`Map<String, Object>`)

---

## 4. 核心测试结果分析

### 4.1 堆内存占用评估 (Memory Footprint)
1. **总体堆内存占用**：5 次测试数据高度一致，常驻 100 万 512 维向量及元数据时，净 JVM 堆内存占用固定为 **3463 MB (约 3.38 GB)**。
2. **单条向量综合成本**：包含连续内存 `float[]` 缓冲区、ID 双向索引、删除位图及元数据 Map，平均单条 512 维向量综合内存消耗约为 **3631 字节 (~3.54 KB)**。
3. **连续内存效果**：通过 `FloatVectorBuffer` 一维平铺存储，避免了 100 万个小 `float[]` 对象的频繁分配，大幅降低了 GC 停顿频次。

### 4.2 写入吞吐量与延迟 (Upsert Performance)
1. **纯写入吞吐量**：单线程下 Upsert 写入吞吐量平均达到 **461,223 ops/sec**，峰值达到 **54.1 万 ops/sec**。
2. **单条写入延迟**：单条向量完成索引映射与写入的微观延迟平均仅为 **2.194 微秒 (μs)**。
3. **全量构建速度**：在单线程模式下，包含随机生成数、对象创建与写入的全过程，100 万向量可在 **9.30 秒** 内全部完成。

### 4.3 磁盘快照刷盘性能 (Snapshot Storage)
1. **快照文件总体积**：全量持久化后生成的文件（包含 `store.json`、`vectors.bin` 和 `documents.jsonl`）总磁容量为 **2.35 GB**。
2. **刷盘效率**：采用物理文件覆盖 (`REPLACE_EXISTING`)，全量刷盘耗时平均为 **10.37 秒**。

---

## 5. 结论与部署建议

1. **资源配置建议**：
   - 如果采用未量化的默认配置存储 100 万向量，推荐分配 `-Xmx4g` 或更高的 JVM 堆内存。
   - 若后续需要将内存压至 1GB 以内，可评估开启 SQ8 标量量化功能（将向量体积压缩约 4 倍）。
2. **生产场景适用性**：
   - 极其适合小规模知识库、FAQ 检索以及百万人群/商品向量检索场景，免去搭建和运维 Elasticsearch 集群的成本。
